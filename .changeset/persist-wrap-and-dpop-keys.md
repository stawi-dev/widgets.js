Fix sign-in not surviving a page reload by persisting the wrap key and
DPoP keypair alongside the encrypted refresh token.

`saveSession` previously dropped both keys on the floor with a "Keys are
not persisted; they must be regenerated by caller" comment — but the
caller (`createWorkerCore`'s init path) doesn't regenerate them. It
checks `loaded.wrapKey` / `loaded.dpopKey`, sees both `undefined`, and
calls `wipe("storage_corruption")` which clears the session and emits a
spurious `storage_corruption` security event. Net effect: every
successful sign-in worked in-memory on the callback page, but the next
page load (e.g. navigating to `/dashboard/`) wiped the session and
reported `unauthenticated` despite valid tokens having been issued.

Non-extractable `CryptoKey` / `CryptoKeyPair` objects are
structured-cloneable per the Web Crypto spec — `extractable: false`
blocks `crypto.subtle.exportKey()` but not the structured clone that
IndexedDB performs internally. The store now writes the keys directly
and reads them back; `isValid` rejects pre-fix sessions (no `wrapKey`/
`dpopKey`) so users on upgrade re-authenticate once cleanly instead of
hitting the corruption path.

Round-trip is covered by a new `store.test.ts` case that re-decrypts
the persisted `wrappedRT` with the loaded `wrapKey`.
